# Quality monitor — alert on quality, not latency

Chapter 9 opens with a bad morning: *"You open the dashboard: traffic
healthy, latency fine, no errors. The agent didn't crash. It just lied — and
nothing you were watching was built to see it."*

This demo is that week, for the [`ask-the-docs`](../ask-the-docs/) tool. The
dashboard stays green. From day 4, travel answers quietly go wrong. The
monitor finds it, alerts on it, walks the trace to the cause, and stops the
bad answers before users see them.

```
 week of traces ─► old dashboard ─► sample & score ─► by segment ─► alert ─► root cause
   (synthetic)       all green       (Demo A's checks)  travel ↓     travel    the index,
                                                                    fires     not the model
                                                          └─► --guard: stop bad answers at runtime
```

It covers the other two of Chapter 9's three places evaluation lives.
[`eval-harness/`](../eval-harness/) is the gate *before* you ship; this is
**production monitoring** (watch it after you ship) and a **runtime
guardrail** (stop the worst of it in the moment).

## Run it

No install, no network, no API key:

```bash
cd demos/quality-monitor
python3 quality_monitor.py            # steps ① to ⑤
python3 quality_monitor.py --guard    # ...and ⑥, the guardrail
python3 quality_monitor.py --day 4    # every trace of day 4, scored
python3 quality_monitor.py --brief    # the tables and verdicts only
python3 test_monitor.py               # the tests → ALL TESTS PASSED
```

## What it does, step by step

**① The old dashboard.** Requests, p50 and p99 latency, and error rate, per
day. All green, all week.

**② Sample & score.** Real volume dwarfs any test set, so you lean on cheaper
scorers and sampling (Chapter 9). Half the traffic is sampled by trace id and
scored with layers 1 and 2 of the [eval harness](../eval-harness/), imported,
not copied: did the answer cite a source, and are the numbers and names it
states in the passage it used? Production has no golden set, so the facts to
check come from the answer itself. The score is written back onto the
generation span as `eval.faithfulness`, as Chapter 9 describes.

**③ By segment.** Daily faithfulness, for all traffic and for each part of
the handbook. The overall line barely moves. Travel falls from day 4.

**④ Alert.** The alert fires when faithfulness for a segment falls below the
threshold. The same rule on the global average never fires, and neither do
the latency and error alerts. A serious problem in one workflow drowns
unnoticed in an average across all of them (Chapter 9).

**⑤ Root cause by elimination.** The failing travel traces from day 4 are
compared with travel traces before it, one part of the response path at a
time: model, prompt, tools, router, retrieval. Chapter 9's experiment: bet,
before you look, that it's the model, and notice how often it isn't. Only
`app.index_version` changed. The monitor then shows what each failing
question retrieved before and what it retrieves now.

**⑥ Guardrail** (`--guard`). The same two checks, run on every response
before the user sees it. An answer that is uncited or not grounded in its
passage becomes an honest refusal: *"I couldn't find that in the handbook."*
Chapter 7 asks for exactly that when retrieval is weak: an honest "I don't
know" rather than a confident fabrication.

## What to watch

The dashboard in step ① is green every day, with p99 latency flat between
1.1 and 1.5 seconds. In step ③ the overall score never drops below 92%, while travel
falls to between 33% and 62% from day 4. Step ④ fires on travel for days 4
to 7, and the three rules a classic setup would have (global average,
latency, errors) never fire. Step ⑤ ends with:

```
It isn't the model. It's retrieval: app.index_version hb-2026-10-01 → hb-2026-10-29.
```

With `--guard`, 48 answers are stopped, 43 of them the stale travel answers.
The guardrail protects users, but the fix is still the index.

## The data is synthetic

[`traces/week.jsonl`](traces/week.jsonl) is **synthetic, for this demo**: one
made-up week of ask-the-docs traffic, about 940 requests. It is generated by
[`make_traces.py`](make_traces.py) with a fixed seed, so it is the same every
time, and a test checks that. Every passage in it is a real line from
[`../ask-the-docs/handbook/`](../ask-the-docs/handbook/).

The scenario: on day 4 the retrieval index is rebuilt, and the rebuild picks
up an old copy of `travel.txt` that lacks two rules (VP approval for trips
over 500 EUR, and manager approval for rental cars). Questions about those
rules now retrieve the wrong passage, and the model answers anyway. Nothing
else changes: the prompt version and the model are the same all week, and
latency and errors stay flat.

Each record is a trace tree grown from [Lab 08](../../labs/08_trace.py)'s
single span: `request → retrieval → generation`. The attribute names follow
the OpenTelemetry GenAI conventions where they exist (`gen_ai.request.model`,
`gen_ai.usage.input_tokens`, `gen_ai.usage.output_tokens`), plus `app.*`
attributes for the rest (`app.segment`, `app.prompt_version`,
`app.index_version`, `app.route`).

## Tuning

| Env var | Default | Meaning |
|---------|---------|---------|
| `QM_SAMPLE_RATE` | `0.5` | share of traffic scored (by trace id, so the same trace is always in or out) |
| `QM_ALERT_THRESHOLD` | `0.85` | faithfulness below this fires the alert |
| `QM_ALERT_WINDOW` | `1` | days averaged for each alert check |
| `QM_MIN_SAMPLES` | `5` | don't alert on fewer scored answers than this |
| `QM_P99_MS` | `3000` | the old latency alert: p99 above this |
| `QM_MAX_ERROR_RATE` | `0.02` | the old error alert: error rate above this |
